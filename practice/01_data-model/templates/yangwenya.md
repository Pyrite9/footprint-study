## 1. 작성 예시: 조(team), 팀 조장 작성

### 1-1. 업무 규칙

1. 과제 하나에는 조가 여러 개 있음. 조는 반드시 과제 하나에 속함
2. 조에는 화면에 보이는 이름이 있음. 예: "1조(Team 1)". 다른 과제에도 같은 이름의 조가 있을 수 있음
3. 조장이 초대 코드를 발급함. 발급하기 전에는 초대 코드가 없음
4. 두 조가 같은 초대 코드를 가질 수 없음. 다시 발급하면 새 코드로 바뀜
5. 조 하나에는 조원이 여러 명 참여함. 참여 기록은 "조 참여" 엔티티가 맡음

### 1-2. 논리적 데이터 모델 — 속성

| 속성명 | 식별자 | 필수 | 근거 규칙 |
|---|---|---|---|
| 조 번호 | 예 | 필수 | 조 이름은 과제마다 겹칠 수 있음(규칙 2). 그래서 번호로 구분함 |
| 조 이름 | 아니오 | 필수 | 규칙 2 |
| 초대 코드 | 아니오 | 선택 | 규칙 3. 발급 전에는 없음. 겹치면 안 됨(규칙 4) |

※ 다른 엔티티를 가리키는 값(어느 과제의 조인지)은 이 표에 쓰지 말고 아래 관계 표에 쓸 것. 물리적 데이터 모델에서 FK 컬럼이 됨

### 1-3. 논리적 데이터 모델 — 관계

| 상대 엔티티 | 관계 | 필수 | 문장으로 읽기 |
|---|---|---|---|
| 과제 | 과제 1 : 조 N | 조 쪽 필수 | 과제 하나는 조를 여러 개 가짐. 조 하나는 반드시 과제 하나에 속함 |
| 조 참여 | 조 1 : 조 참여 N | 조 참여 쪽 필수 | 조 하나에는 조 참여가 여러 개 있음. 조 참여 하나는 반드시 조 하나에 속함 |

### 1-4. 물리적 데이터 모델(PostgreSQL)

테이블 이름: `team`

| 컬럼명 | 데이터 타입 | NULL | 제약조건 | 비고 |
|---|---|---|---|---|
| id | bigint | 불가 | PK | 조 번호. 데이터베이스가 자동으로 번호를 붙임 |
| assignment_id | bigint | 불가 | FK, assignment(id) 참조 | 과제 관계에서 나온 컬럼. 규칙 1의 "반드시" 때문에 NULL 불가 |
| name | varchar(255) | 불가 | 없음 | 조 이름. 겹칠 수 있으므로 UNIQUE를 두지 않음 |
| invite_code | varchar(255) | 허용 | UNIQUE | 발급 전에는 NULL. PostgreSQL은 NULL끼리는 겹침으로 보지 않음. 그래서 발급 전인 조가 여러 개여도 됨 |

테이블 제약: 없음

※ 조 참여 관계는 이 테이블에 컬럼을 만들지 않음. "N" 쪽인 조 참여 테이블에 `team_id` 컬럼이 생김
※ 컬럼 두 개 이상을 쓰는 제약(예: 두 컬럼을 합친 UNIQUE)은 "테이블 제약" 줄에 따로 쓸 것

### 1-5. CREATE TABLE(선택)

```sql
CREATE TABLE team (
    id            bigint       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    assignment_id bigint       NOT NULL REFERENCES assignment (id),
    name          varchar(255) NOT NULL,
    invite_code   varchar(255) UNIQUE
);
```

## 2. 내 엔티티: 회원(member)

### 2-1. 업무 규칙

1. 교수와 학생은 모두 회원임
2. 대부분의 회원은 학교 구글 계정으로 로그인함. 어느 방법으로 로그인하든 이메일 주소가 로그인 아이디임
3. 같은 이메일 주소로 회원이 두 번 만들어질 수 없음
4. 화면에 회원의 이름이 보임
5. 회원 유형은 교수와 학생 두 가지임. 모든 회원은 둘 중 하나임
6. 시연용으로 미리 만들어 둔 계정은 비밀번호로 로그인함. 학교 구글 계정으로 가입한 회원은 비밀번호가 없음
7. 비밀번호는 해시(hash) 값으로 바꿔서 저장함. 해시 값은 원래 비밀번호로 되돌릴 수 없음
8. 교수 회원은 과제를 여러 개 만들 수 있음. 학생 회원은 여러 과제의 조에 참여할 수 있음

## 부록. 데이터베이스 제약조건

- 제약조건은 잘못된 값이 저장되지 않도록 **데이터베이스가 마지막에 막는 규칙**임
- 제약조건을 어기는 값을 저장하려고 하면 데이터베이스가 저장을 거부하고 오류를 돌려줌
- 서버 코드가 먼저 검사해도 제약조건을 데이터베이스에도 둠. 코드에 실수가 있을 수 있기 때문임

| 제약조건 | 뜻 | 예시 | 어기면 |
|---|---|---|---|
| PK(PRIMARY KEY) | 한 행을 다른 행과 구분하는 값. 겹치지 않고 비어 있지 않음. 테이블마다 하나 | 조 번호 `team.id` | 같은 번호의 행을 넣으면 거부 |
| FK(FOREIGN KEY) | 다른 테이블의 PK를 가리키는 값. 가리키는 행이 실제로 있어야 함 | `team.assignment_id`는 `assignment.id`를 가리킴 | 없는 과제 번호를 넣으면 거부. 조가 남아 있는 과제를 지우려고 해도 거부 |
| UNIQUE | 같은 값이 두 번 저장되지 않음. NULL은 여러 개 있어도 됨 | `team.invite_code` | 다른 조와 같은 초대 코드를 넣으면 거부 |
| 복합 UNIQUE | 컬럼 두 개 이상의 **조합**이 두 번 저장되지 않음. 각 컬럼 값은 따로 겹쳐도 됨 | `UNIQUE (조 번호, 회원 번호)`라면 같은 회원이 같은 조에 두 번 들어갈 수 없음 | 같은 조합을 넣으면 거부 |
| NOT NULL | 비어 있으면 안 됨 | `team.name` | 이름 없이 넣으면 거부 |
| CHECK | 값이 조건을 만족해야 함. NULL은 CHECK를 통과하므로 NOT NULL과 함께 사용함 | 나이 컬럼에 `CHECK (age >= 0)` | 음수를 넣으면 거부 |
| DEFAULT | 값을 넣지 않으면 대신 들어갈 기본값. 막는 규칙은 아님. 발자국 1단계에서는 사용하지 않음 | `DEFAULT false`라면 값을 넣지 않았을 때 false가 들어감 | 거부하지 않고 기본값을 넣음 |

- PK, FK, UNIQUE, 컬럼 하나만 쓰는 CHECK는 표의 "제약조건" 칸에 쓸 것
- NOT NULL은 "NULL" 칸에 "불가"로 쓸 것
- 컬럼 두 개 이상을 쓰는 제약(복합 UNIQUE, 두 컬럼을 비교하는 CHECK)은 표 아래 "테이블 제약" 줄에 쓸 것
- 찾아볼 것: `PostgreSQL constraints`, `PostgreSQL 제약조건`
