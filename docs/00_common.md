# 발자국 학습 계획 — 공통 (09.18 ~ 10.16)

이 문서는 전원이 읽습니다. 역할별 할 일은 `01_frontend.md`와 `02_backend.md`에 있습니다. 팀 조장의 할 일은 `03_leader.md`에 있습니다.

## 1. 큰 그림 — 왜 이 순서로 배우는가

발자국은 세 부분으로 되어 있습니다.

- 화면(React): 사용자가 보고 누르는 부분입니다.
- 서버(Spring Boot): 화면의 요청을 받아 처리하는 부분입니다.
- 데이터베이스(PostgreSQL): 과제, 조, 산출물, 평가를 저장하는 부분입니다.

화면이 서버에 요청을 보내고, 서버가 데이터베이스에 저장합니다. 발자국의 모든 기능이 이 구조로 움직입니다.

학습은 4주 동안 두 단계로 진행합니다.

| 기간 | 단계 | 이유 |
|---|---|---|
| 1 ~ 2주차 | 도구 없이 기초를 직접 만듭니다. | React와 Spring Boot는 많은 일을 대신 해 줍니다. 무엇을 대신해 주는지 모르면, 오류가 났을 때 고칠 수 없습니다. |
| 3 ~ 4주차 | 같은 것을 React와 Spring Boot로 다시 만듭니다. | 직접 만든 것과 비교하면 도구가 하는 일이 보입니다. |
| 11월부터 | 발자국의 실제 기능을 만듭니다. | 4주 동안 만든 제출물이 첫 버전이 됩니다. |

## 2. 이 문서를 읽는 방법

- `- [ ]`는 할 일 하나입니다. 끝내면 `- [x]`로 바꿉니다.
- "찾아볼 것"은 검색어입니다. 영어 검색어는 그대로 검색합니다.
- "왜 배우는가"는 그 주의 내용이 발자국의 어디에 쓰이는지 설명합니다.
- "제출물"은 그 주에 PR로 올려야 하는 결과입니다. PR은 "내 작업을 원본에 합쳐 달라는 요청"입니다. 방법은 4절에 있습니다.
- "※ 용어"는 그 주에 처음 나오는 단어의 뜻입니다.

## 3. 규칙

- 매주 일요일 밤까지 제출물을 PR로 올립니다.
- 매주 월요일에 30분 동안 함께 확인합니다. 10.05(월)은 공휴일이므로 그 주는 10.06(화)에 확인합니다.
- 30분 넘게 막히면 단체방에 질문합니다. 혼자 오래 붙잡지 않습니다. 질문할 때는 오류 문구를 그대로 붙여 넣습니다.
- 공식 문서를 먼저 봅니다. MDN, javascript.info, react.dev는 한국어와 중국어 번역이 있습니다.
- 제출하는 코드에는 주석을 씁니다. 함수와 클래스마다 "무엇을 하는지" 한 줄을 씁니다. 본인 말로 씁니다. 한국어, 영어, 중국어 모두 됩니다.
- 이해하지 못한 줄에는 `?`를 넣은 주석을 답니다. 예: `// ? 이 줄이 왜 필요한지 모르겠다`. 모르는 것을 표시해도 불이익은 없습니다. 월요일에 함께 봅니다.
- AI 도구를 써도 됩니다. 단, 주석은 직접 씁니다.
- 설치와 환경 확인은 1주차에 모두 끝냅니다. 추석 연휴(09.24 ~ 09.26) 전에 끝냅니다.
- 2주차는 분량이 가장 많습니다. 8시간 정도 필요합니다.
- 4주차는 중간고사 직전입니다. 분량을 줄였습니다. 줄인 항목은 11월 첫 주에 합니다. 4주차 제출 마감은 일요일이 아니라 10.16(금) 밤입니다. 4주차 확인은 모이지 않고 PR 댓글로 합니다.

## 4. 제출 방법

1. 월요일에 main branch로 이동합니다(`git switch main`). 최신 내용을 받습니다(`git pull`). 그다음 새 branch를 만듭니다. branch 이름은 `영문이름/week1` 형식입니다. 지난주 branch 위에서 새 branch를 만들지 않습니다.
2. 본인 폴더 `members/영문이름/week1/` 안에서만 작업합니다. 다른 사람의 폴더는 고치지 않습니다.
3. 폴더 이름과 파일 이름은 영문으로 씁니다. 한글 경로에서는 Java와 Node.js 도구가 오류를 내는 일이 있습니다.
4. 작업 중간에도 commit과 push를 합니다. 일요일에 한 번에 올리지 않습니다.
5. 일요일 밤까지 PR을 만듭니다. 제목은 `[1주차] 이름` 형식입니다.
6. PR 본문에 그 주의 체크리스트를 붙여 넣습니다. 끝낸 항목은 `- [x]`로 바꿉니다. "막힌 점"도 적습니다.
7. 월요일 확인이 끝나면 팀 조장이 merge 합니다.
8. 3주차와 4주차에는 팀 조장이 만든 예시 프로젝트를 본인 폴더에 복사해서 고칩니다.

※ 용어 — 저장소(repository): 코드를 모아 두는 곳 · branch: 원본을 건드리지 않고 따로 작업하는 가지 · commit: 변경 내용을 기록하는 것 · push: 내 컴퓨터의 기록을 GitHub에 올리는 것 · PR(Pull Request): 내 작업을 원본에 합쳐 달라고 요청하는 것 · merge: 합치는 것

## 5. 1주차 공통 (09.18 ~ 09.27) 전원

**왜 배우는가**
발자국은 6명이 같은 코드를 함께 고칩니다. Git과 PR은 서로의 코드를 덮어쓰지 않고 합치는 방법입니다. HTTP는 화면(React)과 서버(Spring Boot)가 대화하는 방식입니다. 프론트엔드와 백엔드 모두 이 대화를 읽을 수 있어야 합니다. 그래야 오류가 났을 때 어느 쪽 문제인지 알 수 있습니다.

### 환경 확인

- [ ] Git이 설치되어 있는지 확인합니다. 터미널에서 `git --version`을 실행합니다. 없으면 설치합니다.
  - 찾아볼 것: `git install windows`
- [ ] VS Code가 설치되어 있는지 확인합니다.
- [ ] GitHub 계정 아이디를 팀 조장에게 보냅니다. 저장소 초대 메일을 수락합니다.

### Git

- [ ] 터미널에서 폴더를 이동하고 파일 목록을 봅니다.
  - 찾아볼 것: `terminal cd ls basics`
- [ ] 저장소를 내 컴퓨터로 가져옵니다.
  - 찾아볼 것: `git clone`
- [ ] branch를 만듭니다. 이름은 `영문이름/hello`입니다.
  - 찾아볼 것: `git switch -c`
- [ ] `members/영문이름/` 폴더를 만들고, 그 안에 `hello.md` 파일을 만듭니다. commit과 push를 합니다.
  - 찾아볼 것: `git add commit push`
- [ ] 저장소 맨 위의 `members.md` 파일에 본인 이름을 한 줄 추가합니다. 여러 명이 같은 파일을 고치므로 충돌(conflict)이 날 수 있습니다. 충돌이 나면 해결합니다.
  - 찾아볼 것: `git merge conflict resolve vscode`
- [ ] GitHub에서 PR을 만듭니다. merge 될 때까지 확인합니다. 이 PR은 추석 연휴 전(09.23)까지 올립니다.
  - 찾아볼 것: `github create pull request`

### HTTP

- [ ] HTTP 요청과 응답이 무엇인지 읽습니다. GET, POST, PUT, DELETE의 차이를 말할 수 있어야 합니다.
  - 찾아볼 것: `MDN HTTP overview`, `MDN HTTP request methods`
- [ ] status code 200, 201, 400, 401, 404, 500의 뜻을 읽습니다.
  - 찾아볼 것: `MDN HTTP status codes`
- [ ] JSON 형식을 읽습니다.
  - 찾아볼 것: `MDN JSON`
- [ ] 브라우저에서 F12를 누르고 Network 탭을 엽니다. 요청 1개를 골라 method와 status를 확인합니다.
  - 찾아볼 것: `chrome devtools network tab`

**제출물:** merge 된 PR 1개(`hello.md`와 `members.md`). 1주차에는 PR을 2개 올립니다. 이 PR이 첫 번째입니다. 두 번째는 역할 문서의 1주차 제출물이며 09.27(일) 밤까지 올립니다.

※ 용어 — 충돌(conflict): 두 사람이 같은 줄을 다르게 고쳐서 Git이 자동으로 합치지 못하는 상태 · HTTP: 화면과 서버가 주고받는 요청과 응답의 규칙 · method: 요청의 종류(GET은 조회, POST는 생성, PUT은 수정, DELETE는 삭제) · status code: 서버가 돌려주는 결과 번호 · JSON: 화면과 서버가 데이터를 주고받을 때 쓰는 글자 형식
