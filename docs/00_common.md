# 발자국 학습 계획 2단계 — 공통 (10.19 ~ 11.15)

이 문서는 전원이 읽습니다. 역할별 할 일은 `01_frontend.md`와 `02_backend.md`에 있습니다. 팀 조장의 할 일은 `03_leader.md`에 있습니다. 1단계(09.18 ~ 10.16) 문서는 `docs/phase1/`에 있습니다.

## 1. 무엇이 바뀌는가

1단계에서는 연습용 "과제 목록" 프로그램을 만들었습니다. 2단계에서는 발자국의 실제 기능을 사람마다 나누어 맡아서 만듭니다.

2단계에서 만든 코드는 11.16부터 발자국 본 저장소로 옮깁니다. 2단계의 제출물이 곧 발자국의 기능입니다.

1단계 문서의 "11월 첫 주 예정" 항목은 2단계 6주차와 7주차에 들어 있습니다. 1단계에서 10.16에 예정했던 로그인 골격은 10.25 골격에 들어 있습니다.

## 2. 왜 이 기간에 이것을 하는가

- 12.11(금)에 학기 발표가 있습니다. 과제 생성, 역할 배정, 산출물 업로드, 동료평가 입력이 이어지는 흐름 1개를 시연합니다.
- 12.15(화)까지 산업체 연계 PBL 결과물을 제출합니다. 실제로 동작하는 서비스를 제출해야 합니다.
- 11.16부터는 각자의 기능을 합치고 고치는 기간입니다. 그래서 각자의 기능은 11.15까지 다른 사람의 코드 없이 본인 컴퓨터에서 실행해도 동작해야 합니다.

담당 기능은 12.11 시연 흐름에 들어가는 것만입니다. 완료확인, 기여 항목, 근거 패널, 교수 열람, 조 단위 권한은 12.12 이후에 만듭니다.

## 5. API 명세와 골격

**API 명세 (`docs/api.md`, 10.22 공개)**

API 명세는 화면과 서버가 주고받는 주소와 데이터 모양을 적은 문서입니다. 프론트엔드와 백엔드 모두 이 문서를 기준으로 만듭니다. 화면마다 주소와 담당자를 적은 "화면 표"와 화면 그림도 이 문서에 있습니다.

- 명세와 다르게 만들고 싶으면 먼저 단체방에서 팀 조장에게 말합니다. 혼자 바꾸지 않습니다. 한 사람이 바꾸면 함께 맞출 사람의 코드가 동작하지 않기 때문입니다.
- 명세에 빠진 것이 보이면 단체방에 알립니다.
- 명세가 바뀌면 팀 조장이 `docs/api.md`의 "변경 기록"에 날짜와 영향을 받는 사람을 적고 단체방에 알립니다.

**골격 (`skeleton/`, 10.25 공개)**

골격은 발자국의 뼈대 프로젝트입니다. 1단계의 예시 프로젝트(`example/`)와 같은 구조와 규칙을 따릅니다. 골격에는 다음이 들어 있습니다.

- 백엔드: 로그인, 회원, 파일 저장, 엔티티 6개와 Repository, 오류 응답 처리, 시작 데이터
- 프론트엔드: 로그인 화면, 화면 이동 설정, 로그인 정보를 붙여서 요청하는 공통 함수, 담당 화면의 빈 파일, 가짜 API, 동료평가 항목과 행동 기준 문장

각자는 담당 기능만 채웁니다. 다음 규칙을 지킵니다.

- 로그인, 보안 설정, 파일 저장 설정은 직접 만들지 않습니다.
- 골격의 공통 파일은 고치지 않습니다. 공통 파일 목록은 `skeleton/README.md`에 있습니다. 고칠 일이 있으면 팀 조장에게 말합니다.
- 담당 엔티티에 메서드를 추가하는 것은 됩니다. 필드를 추가하거나 바꾸려면 먼저 팀 조장에게 묻습니다.
- 골격이 바뀌면 팀 조장이 `skeleton/CHANGELOG.md`에 적고 단체방에 알립니다. 바뀐 파일만 본인 폴더에 다시 복사합니다.

## 6. 팀 조장의 시연본

팀 조장은 12.11 흐름 전체가 동작하는 시연본을 따로 만듭니다. AI 도구를 사용해서 만듭니다. 목적은 두 가지입니다.

- 12.15 결과물 제출 기한을 반드시 지키기 위한 대비입니다.
- 11.16 이후 각자의 기능을 합칠 때 기준이 됩니다.

시연본은 11.15까지 공개하지 않습니다. 시연본에는 각자의 담당 기능을 완성한 코드가 들어 있기 때문입니다. 11.16에 담당자별로 읽을 파일 목록과 함께 공개합니다.

11.16부터 각자 만든 기능이 시연본의 같은 부분을 대체합니다. 11.28 전후로 기능마다 "본인 코드"와 "시연본" 중 무엇을 시연에 쓸지 정합니다. 기준은 두 가지입니다.

1. 시험용 Postman 모음(11.08 공개)을 통과합니다. 시연본도 같은 모음으로 시험합니다.
2. 담당자가 코드를 5분 동안 설명할 수 있습니다.

시연본을 쓰게 된 기능도 담당자는 바뀌지 않습니다. 발표의 질의응답에서는 각자 담당 기능을 설명합니다. 그래서 담당자는 시연본의 해당 부분도 읽고 설명할 수 있어야 합니다.

## 7. 규칙

1단계 3절과 4절의 규칙을 따릅니다. 다만 아래 규칙이 1단계 규칙보다 우선합니다.

**작업 폴더와 branch**

- 5주차는 1단계처럼 `members/영문이름/week3/`, `week4/` 폴더를 씁니다. branch 이름은 `영문이름/week3`, `영문이름/week4`입니다.
- 6주차부터는 `members/영문이름/footprint/` 폴더 하나에서 계속 작업합니다. 주마다 새로 복사하지 않습니다.
- 6주차부터 branch 이름은 `영문이름/week6` 형식입니다. PR 제목은 `[6주차] 이름` 형식입니다.
- 아래 두 규칙은 6주차부터 적용합니다. 5주차의 branch는 역할 문서의 5주차를 따릅니다.
- 지난주 PR이 merge 되었으면, 월요일 확인 뒤에 main에서 새 branch를 만듭니다.
  - 찾아볼 것: `git switch main`, `git pull`, `git switch -c`
- 지난주 PR이 아직 merge 되지 않았으면, 새 branch를 만들지 않습니다. 지난주 branch에서 계속 작업하고 같은 PR에 push 합니다. PR 제목의 주차만 바꿉니다.
- IntelliJ로는 본인의 `footprint/backend` 폴더만 엽니다. 저장소 전체를 열면 여러 사람의 프로젝트 이름이 겹쳐서 인식되지 않습니다.
- `db.json`은 레코드 추가만 commit 합니다. 필드 이름과 모양은 바꾸지 않습니다. 모양은 API 명세를 따릅니다.

**PR을 만들기 전에**

- GitHub의 PR 화면에서 "Files changed" 탭을 엽니다. 본인 폴더 밖의 파일이 바뀌거나 지워졌으면 PR을 만들지 않고 팀 조장에게 묻습니다. main이 아닌 branch에서 새 branch를 만들면, 본인이 고치지 않은 변경이 PR에 함께 들어갈 수 있습니다.
- GitHub 웹 화면에서 파일을 올리지 않습니다. 본인 컴퓨터에서 `git push`로 올립니다. 웹으로 올리면 `node_modules` 같은 올리면 안 되는 파일이 걸러지지 않습니다.

**확인**

- 매주 월요일 30분 동안 함께 확인합니다. 5주차(중간고사)는 모이지 않고 PR 댓글로 확인합니다.
- 7주차부터 PR의 Reviewers에 "함께 맞출 사람"을 지정합니다. 짝은 데이터 모양이 API 명세와 같은지만 봅니다. 코드의 좋고 나쁨은 보지 않습니다. 짝 확인은 월요일 확인 전까지 PR 댓글로 끝냅니다.

**그 밖의 규칙**

- AI 도구를 써도 됩니다. 주석은 직접 씁니다. AI가 만든 줄도 본인이 설명할 수 있어야 합니다. 발표에서 교수님이 담당 기능에 대해 질문할 수 있습니다.
- 분량은 한 주에 프론트엔드 8 ~ 12시간, 백엔드 10 ~ 14시간 정도입니다. 그 시간을 쓰고도 끝나지 않으면 역할 문서의 "밀리면 뒤로 보내는 순서"를 따릅니다. 미룬 항목은 PR 본문의 "막힌 점"에 적습니다.
- 역할 문서의 "11.15 최소선" 항목은 뒤로 보내지 않습니다.
- 30분 넘게 막히면 단체방에 질문합니다. 오류 문구를 그대로 붙여 넣습니다.

## 8. 제출물을 통과하지 못하면

통과 기준은 세 가지입니다.

1. 제출물이 설명대로 동작합니다.
2. 코드에 본인이 쓴 주석이 있습니다.
3. 데이터 모양이 API 명세와 같습니다.

- 1단계 7절의 10.16 판정은 5주차 마감(10.25)으로 미룹니다.
- 6주차와 7주차 제출물이 월요일 확인에서 통과하지 못하면 1주 더 시간을 줍니다. 이때 그 다음 주의 "밀리면 뒤로 보내는 순서"를 바로 적용합니다. 1주 더 받은 일과 다음 주 일을 함께 하면 분량이 넘치기 때문입니다.
- 11.15에 동작하지 않는 부분은 시연본을 씁니다. 그 경우 11.16 이후에는 시연본의 해당 부분을 읽고 설명하는 일, 시연 시나리오 시험, 시작 데이터 작성을 맡습니다.
