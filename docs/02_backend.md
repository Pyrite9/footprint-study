## 6주차 (10.26 ~ 11.01) — 골격 실행, 첫 API

**왜 배우는가**
골격에는 엔티티와 Repository가 이미 있습니다. 이번 주에는 그 위에 Service, Controller, DTO를 써서 화면이 부를 수 있는 API를 만듭니다. 5주차에 고친 예시의 `Assignment`와 같은 모양입니다. 다른 점은 두 가지입니다. 첫째, 골격의 API는 로그인한 사용자만 부를 수 있습니다. 그래서 Postman으로 부를 때 로그인해서 받은 token을 함께 보냅니다. 둘째, 발자국의 목록은 대부분 조건이 붙습니다. 예를 들어 "1조의 산출물 목록"입니다. 그래서 Repository에 조건 조회 메서드를 직접 추가합니다.

### 골격 실행

- [ ] 골격의 `skeleton/backend`를 `members/영문이름/footprint/backend/`로 복사하고 `skeleton/README.md`대로 실행합니다. 10.28(수)까지 실행되지 않으면 단체방에 오류 문구를 올립니다.
- [ ] Postman으로 로그인 API를 불러서 token을 받습니다. 그 token을 Authorization 헤더에 넣고 "내 정보" API를 부릅니다. token 없이 부르면 401이 나오는 것도 확인합니다. 시작 계정은 `skeleton/README.md`에 있습니다.
  - 찾아볼 것: `postman bearer token authorization`
- [ ] 로그인한 회원을 Controller에서 받는 방법을 골격 README에서 찾아 읽습니다. 예시 Controller에 주석을 씁니다.
- [ ] 본인 담당 엔티티를 엽니다. 클래스마다 맨 위에 "이 클래스가 하는 일"을 본인 말로 한 줄 씁니다. `@ManyToOne`이 붙은 필드에는 "어느 엔티티를 가리키는지" 주석을 씁니다.
  - 이종민: 과제, 조, 조 참여
  - 장호진: 산출물, 평가
  - 찾아볼 것: `jpa manytoone example`
- [ ] `docs/api.md`에서 본인 담당 API를 찾아 PR 본문에 표로 옮겨 적습니다. 열은 method, 주소, 요청, 응답, 오류 code입니다.
- [ ] Node.js 24를 설치합니다. 8주차에 함께 맞출 사람의 화면을 본인 컴퓨터에서 실행할 때 씁니다.
  - 찾아볼 것: `node.js 24 lts download`

### 담당 API

- 이종민
  - [ ] 과제 목록 API를 만듭니다.
  - [ ] 과제 한 건 조회 API를 만듭니다. 없는 번호는 404 `NOT_FOUND`입니다.
  - [ ] 과제 생성 API를 만듭니다. 과제명과 기간을 받습니다. 과제를 만든 교수는 요청에서 받지 않고 로그인한 회원으로 넣습니다. 번호로 회원을 찾는 방법은 7주차 "공통"의 첫 항목을 먼저 읽습니다.

  - [ ] Postman으로 만든 API를 모두 부르고 캡처합니다.

## 7주차 (11.02 ~ 11.08) — 연결된 데이터 저장하기

**왜 배우는가**
발자국의 데이터는 서로 연결되어 있습니다. 과제 아래에 조가 있고, 조 아래에 조원이 있습니다. 산출물은 산출물을 올린 조원을 가리킵니다. 이번 주에는 다른 엔티티를 가리키는 데이터를 저장합니다. 저장하기 전에 가리킬 대상을 Repository로 먼저 찾아야 합니다. 대상이 없으면 404를 돌려줍니다.

### 공통

- [ ] 연결된 엔티티를 저장하는 순서를 익힙니다. "번호로 대상을 찾는다 → 없으면 `NotFoundException` → 있으면 새 엔티티에 넣고 저장한다"입니다.
  - 찾아볼 것: `spring data jpa findById orElseThrow`, 예시의 `AssignmentService.java`
- [ ] 저장을 두 번 이상 하는 Service 메서드에는 `@Transactional`을 붙입니다. 이유는 `docs/decisions.md`에 있습니다.
  - 찾아볼 것: `spring @Transactional 기초`

### 담당 API

- 이종민
  - [ ] 과제 아래에 조를 만들고 조장을 지정하는 API를 만듭니다. 조장은 회원 번호로 받습니다. 조장을 어디에 저장하는지는 `docs/api.md`를 따릅니다.
  - [ ] 과제의 조 목록 API를 만듭니다. 과제 상세 화면에서 씁니다.
  - [ ] 조원 목록 API를 만듭니다. 조원마다 이름과 역할명을 돌려줍니다. 이번 주에는 골격의 시작 데이터에 들어 있는 조원으로 확인합니다.
- 장호진
  - [ ] 산출물 업로드 API를 아래 순서로 만듭니다. 한 단계가 Postman에서 동작하면 다음 단계로 갑니다. PR 본문에 몇 단계까지 했는지 적습니다.
    1. 파일을 받아서 파일 이름과 크기만 응답합니다.
    2. 받은 파일을 골격의 파일 저장 클래스(`StorageService`)에 넘깁니다. MinIO 관리 화면(http://localhost:9001)에서 파일이 보이는지 확인합니다.
    3. `StorageService`가 돌려준 파일 위치를 산출물 정보와 함께 저장합니다.
    4. 같은 조, 같은 역할의 산출물은 버전 번호가 1씩 늘어나게 합니다. 마지막 버전 번호를 Repository로 찾아 1을 더합니다.
    - 찾아볼 것: `spring boot MultipartFile upload`, `postman form-data file upload`, `spring data jpa findTop orderBy`
    - Postman form-data의 key 이름은 Controller 매개변수의 이름과 같아야 합니다.
  - [ ] 파일이 비었는지는 Service에서 `file.isEmpty()`로 확인합니다. 비었으면 골격의 입력 오류 예외를 던집니다. 파일 요청에는 `@Valid`가 그대로 적용되지 않기 때문입니다.
  - [ ] 업로드 시각은 서버가 넣습니다. 요청에서 받지 않습니다. 발자국의 운영 원칙 "기록 시각은 서버가 남긴다"입니다.
    - 찾아볼 것: `hibernate @CreationTimestamp`
  - [ ] 서버를 다시 시작하면 데이터베이스의 산출물 정보는 지워지고 MinIO의 파일은 남습니다. `ddl-auto: create` 설정 때문입니다. 버전 번호 캡처는 서버를 다시 시작하지 않은 상태에서 찍습니다.

**제출물:** 담당 API와 Postman 캡처. 장호진은 MinIO 관리 화면에서 올린 파일이 보이는 캡처를 함께 냅니다. 마감은 11.08(일) 밤입니다.

**밀리면 뒤로 보내는 순서:**
- 이종민: 조 목록 API(8주차로. 김효민과의 연결은 조 목록 없이 합니다). 조원 목록 API는 윤장현의 연결 대상이므로 미루지 않습니다.
- 장호진: 업로드 4단계 버전 번호(8주차로. 그때까지는 1로 고정)

※ 용어 — `@Transactional`: 여러 저장 작업을 하나로 묶어서, 중간에 실패하면 모두 취소하는 표시 · MultipartFile: 요청으로 받은 파일을 Spring에서 다루는 형식 · form-data: 파일을 담아 보내는 요청 형식 · MinIO: 파일을 저장하는 서버 · `@CreationTimestamp`: 저장할 때 서버의 현재 시각을 자동으로 넣는 표시 · 버전 번호: 같은 역할의 파일을 다시 올릴 때마다 1씩 늘어나는 번호 · `ddl-auto: create`: 서버를 시작할 때마다 테이블을 지우고 새로 만드는 설정

## 8주차 (11.09 ~ 11.15) — 마무리, 화면과 연결

**왜 배우는가**
이번 주에는 시연 흐름의 "역할 배정"과 "동료평가 입력"에 필요한 나머지 부분을 만듭니다. 그러면 담당 기능이 모두 갖춰집니다. 그리고 처음으로 함께 맞출 사람의 화면과 본인의 서버를 연결합니다. 화면에서 버튼을 눌렀을 때 본인의 API가 불려야 실제로 쓸 수 있는 기능입니다.

### 담당 API

- 이종민
  - [ ] 조를 만들 때 초대 코드를 함께 만들어 저장합니다.
    - 찾아볼 것: `java UUID randomUUID`
  - [ ] 초대 코드로 조에 합류하는 API를 만듭니다. 로그인한 회원이 그 조의 조원으로 저장됩니다. 없는 초대 코드는 404 `NOT_FOUND`입니다. 같은 회원이 다시 합류할 때의 처리는 `docs/api.md`를 따릅니다.
    - 찾아볼 것: `spring data jpa findBy optional`
  - [ ] 역할 배정 API를 만듭니다. 조원 한 명의 역할명을 저장합니다.
    - 찾아볼 것: 예시의 `AssignmentService.update`, `spring boot @PatchMapping`
- 장호진
  - [ ] 동료평가 저장 API에서 평가하는 사람을 요청의 번호가 아니라 로그인한 회원으로 바꿉니다. 평가 결과를 다른 사람 이름으로 넣을 수 없게 하기 위해서입니다.
  - [ ] 같은 사람이 같은 조원을 두 번 평가하면 409 `DUPLICATE`를 돌려줍니다. 이 code와 예외 클래스는 골격에 있습니다.
    - 찾아볼 것: `spring data jpa existsBy`

### 화면과 연결

연결 날짜는 11.09(월) 확인에서 정합니다. 11.13(금)까지 대면으로 합니다. 팀 조장이 함께 있습니다. 연결 대상은 7주차까지 만든 API입니다. 8주차에 만든 API는 11.16 이후에 연결합니다.

- [ ] 연결 전날, 함께 맞출 사람의 화면을 본인 컴퓨터에서 혼자 실행해 둡니다. 저장소를 다른 폴더에 한 번 더 clone 하고, 그 폴더에서 상대의 branch로 바꿉니다. 본인 작업 폴더에서는 branch를 바꾸지 않습니다. 화면 폴더에 `.env.local` 파일이 있으면 지웁니다. 로그인 화면까지 열리면 됩니다.
  - 상대가 단체방에 알려 준 branch로 바꿉니다.
  - 찾아볼 것: `git clone`, `git switch branch이름`, `skeleton/README.md`의 "실제 백엔드에 연결"
  - 이종민은 김효민, 윤장현의 화면을 각각 실행합니다.
  - 장호진은 양원야의 화면을 실행합니다.
- [ ] 연결하는 날, 본인 서버와 상대의 화면을 함께 실행합니다. 화면에서 버튼을 눌러 본인 API가 불리는지 확인합니다.
- [ ] 데이터 모양이 맞지 않으면 API 명세를 기준으로 고칩니다. 화면 코드는 상대가 본인 컴퓨터에서 고치고 push 합니다. 본인은 다시 받아서 실행합니다. 명세가 틀렸으면 팀 조장에게 알립니다.
- [ ] 브라우저 개발자 도구(F12)의 Network 탭에서 본인 API가 200으로 응답한 화면을 캡처합니다.
- [ ] 장호진과 양원야는 산출물 업로드를 가장 먼저 연결합니다. 업로드는 실제 서버에서 처음 시험하는 기능이라 문제가 가장 많이 나옵니다. 연결이 되지 않으면 그 자리에서 팀 조장과 함께 원인을 찾습니다. 업로드 화면이나 업로드 API가 준비되지 않았으면 산출물 목록부터 연결합니다.
